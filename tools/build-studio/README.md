# 构建工作台：交互原型与后续约定

这是构建配置的可视化讨论工具，不是新的构建系统。
核心框架、CMake、SDK 与组件不依赖这个工具，删除 tools/ 不影响原有构建。

## 打开与试用

直接用浏览器打开 tools/build-studio/index.html，无需 npm、Node 或后台服务。
也可以在 roboframe 根目录运行：

~~~sh
python3 -m http.server 8766 --bind 127.0.0.1
~~~

然后访问 http://localhost:8766/tools/build-studio/index.html。
只绑定本机；退出服务不影响已保存的文件。

可以依次尝试：
1. 当前骨架：切换 sample-accumulator 的源码/安装包，查看已有 CMake 命令。
2. 未来导航示意：planner 源码 + VIO/controller 安装包，观察相同公开 target 的接入方式。
3. 选择 ARM64：查看待配置条件，导出配置意图 JSON。
4. 恢复默认：回到当前源码构建。

复制与导出按钮真实可用。页面不执行构建、不扫描文件、不下载依赖、不检测平台，
没有假进度或假构建成功提示。安装包路径是示例，必须由使用者提供真实开发包。
导出的 JSON 是讨论用意图文件，不是 CMakePresets.json，当前 CMake 不读取它。
页面刷新后回到默认值，不自动保存机器路径。

## 当前能力与设计预览

| 能力 | 当前状态 |
|---|---|
| 当前骨架整体 SOURCE / PACKAGE 切换 | 输出已有 CMake 支持的命令 |
| 测试开关、源码组件独立 main 开关 | 对应现有 CMake 选项 |
| 混合来源选择 | UI 可操作；不生成伪造 CMake 命令 |
| ARM64 交叉编译 | 只展示意图与缺失条件 |
| 一键执行、日志、取消、失败定位 | 延后实现 |
| 包版本/文件存在性/工具链检测 | 延后实现，不能将 UI 选中视为验证通过 |

全部使用 PACKAGE 时，组件独立 main 选项禁用：
当前组件包只导出库和头文件，主工程只能运行它自己的 IPC 测试。
默认源码构建使用本地 SDK；全包构建使用已安装 SDK。
未来混合模式在示例中统一使用 SDK 安装包，这是一种开发配置，不是永远禁止 SDK 源码开发。

命令的构建目录按目标平台和来源模式分开，避免当前两种模式混用缓存。
选择 ARM64 不会自动下载交叉编译器，也不等于一个有效的 ARM 构建环境。

## 维护这个小 demo

- catalog.js：唯一的 UI 组件/场景/平台清单。
- planner.js：把选择变为配置意图；仅为已支持组合生成命令。
- app.js：控件绑定、复制与导出。
- index.html / style.css：页面呈现。
- check.cjs：可选的 Node 标准库自测，不是工具运行依赖。

新增 demo 组件时，在 catalog.components 增加元数据，并在场景的 components/defaults
中引用；界面自动产生来源选择器，不逐个修改 HTML 或 app.js。
未实现的组件保持 implemented:false，未接入构建的场景保持 buildReady:false。
修改清单只更新 UI，**不会自动把组件加入 CMake 或产品 integration**。
只有实际构建与验证完成后才能将 buildReady 改为 true。

~~~sh
node tools/build-studio/check.cjs
~~~

## 后续正式实现：先完善 CMake，再让 UI 调用

~~~text
产品构建配置（所需组件、来源、目标环境）
           ↓
组件描述 / 安装包描述 → 工具展示与校验
           ↓
CMake 配置 → 编译 → 测试
           ↑
CLI 与 UI 使用同一入口
~~~

保留以下约定即可，不需要现在实现包管理器或插件系统：

### 组件来源与发现

- 每个组件对外提供稳定、带命名空间的 CMake target；源码和安装包使用同一名字。
- 构建配置按组件选择 SOURCE / PACKAGE；缺少所选来源直接报错，不偷偷回退。
- 源码模式只声明本组件公开依赖；安装包通过 CMake config/export 描述传递依赖。
- 产品配置声明 integration 所需的组件；“不需要组件”与“用安装包代替源码”分开。
- 组件数量增长后，再把当前 demo 清单替换成组件自有的简短描述文件；
  安装包也携带该描述，产品索引可以引用描述与包名，不要求源码目录存在。
- 不只扫描 components/ 来发现能力，否则没有拉 VIO 源码就会丢失 VIO 的安装包选项。
- 描述只提供构建与展示元数据，不复制组件运行时 contract。包依赖最终仍由 CMake 校验。
- 一份已解析的组件索引同时服务 UI/CLI，避免长期维护两套互不一致的组件列表。
  当前 catalog.js 是原型数据，不是新增的正式框架契约。

建议将来描述的最少信息是：id、显示名、包名、公开 target、源码位置、
SDK/契约要求。版本信息应来自正式 VERSION/包元数据，避免多处手写。
SOURCE/PACKAGE 是开发或产品配置，不固定写死在组件自己的描述中。

### x86 与 ARM

- 区分宿主平台、目标平台；ARM 既可交叉编译，也可在 ARM 上本机构建。
- 正式选择的是“目标工具链配置”，不能只有一个 CPU 下拉框。
- ARM 配置应明确工具链文件、编译器、sysroot、目标 SDK/组件包前缀；
  包需要匹配目标架构、ABI、标准库和构建选项，版本相同仍可能无法链接。
- 一个构建中只选一份目标 SDK。不能让各组件各自引入不同 SDK。
- 按工具链配置和构建类型隔离 build 目录；更换工具链不得复用旧缓存。
- 交叉编译测试不直接在 x86 宿主运行 ARM 程序。将“编译”和“目标机测试”分开，
  真正有远程运行器或仿真器之后再提供运行按钮。
- 这些都是构建层约束，不要求 component 的数据接口感知 CPU 或编译方式。
  具体算法内的架构相关实现仍由组件维护者负责。

### UI 只做操作入口

框架稳定后，让 CLI/UI 共用 CMake 选项或正式 presets，避免 UI 成为第二套构建引擎。
CMake 必须先能独立完成逐组件混合构建，再接 UI 的配置、构建、测试按钮。
本地执行入口只接受明确的操作与参数数组，不接受页面传入任意 shell 命令。
进程退出码和实际日志决定成功/失败；取消构建需要真正结束构建进程。

届时把这里的“配置意图”映射到正式配置格式，再决定是否需要导入、预设保存、
安装包仓库或自动扫描。当前不承诺原型 JSON 的兼容性，也不提前实现这些机制。

## 本轮验证

已验证当前 SOURCE/PACKAGE 命令生成、测试开关、安装包模式禁用组件 main、
参数引用、无效路径拦截、混合/ARM 预览限制，以及增加清单项无需修改生成逻辑。
浏览器中检查源码/安装包/未来组合切换与页面布局。没有执行 ARM 编译或混合构建。
