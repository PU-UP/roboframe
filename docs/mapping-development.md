# 建图开发计划与边界

基线：dd998ab / codex/initial-framework。开发分支：codex/mapping-pipeline。
所有功能与提交留在开发分支，不自动合回基线。history 原始数据只读，不纳入 Git。

## 分步骤验收

1. 构建基础：逐组件 SOURCE/PACKAGE、显式选择一份 SDK、VERSION 改动自动重新配置。
   保留原有整体安装包选项与累加器入口；分别提交，便于主线挑选。
2. 强类型多组件：odom-buffer、occupancy-grid、map-store；
   组件各自拥有接口、实现、CMake 和测试，只依赖公共 SDK。
3. integration：装配与生命周期、时间匹配数据路由、建图业务状态。
   scan 必须有同时间或前后 odom 插值，不能取任意“最新”位姿。
4. IPC：独立 odom/scan 数据输入，以及 BEGIN/FINISH/SAVE 指令与对应回执。
   结束前缺失位姿的 scan 有明确丢弃统计；结束后 odom 继续输入但地图冻结。
5. 实际日志回放：外部 Python 读 history 中 Intel 数据，经进程管道输入 C++。
   保存地图、重载核对、提前结束后冻结检查、可视化地图成长和轨迹回放。
6. 复核：单元/IPC/真实数据、组件独立构建和混合包构建，记录问题、改进与合并范围。

## 保持精简的决策

- 建图流程属于 integration。栅格累积组件不维护产品流程或伪造 action 状态。
- 里程计组件使用录制的外部估计并提供有界时间历史，不声称实现 VIO/LIO。
- 栅格组件做射线更新；没有 scan matching 或回环，原始 odom 漂移会保留。
- 共用 SDK 只增加确实跨组件传递的二维位姿和地图值类型；不引入中央万能 Data。
- 传感器扫描使用只读共享所有权；地图快照只在明确请求/结束时生成。
- 执行仍为单线程串行，不引入调度器、线程池、插件系统、BT 或 ROS。
- 存储独立组件处理版本化地图文件；输出目录由宿主配置。保存成功与内存完成分开。
- UI 构建工具不参与此次运行链路。命令行与 CMake 是可独立使用的底层入口。

数据为 raw-log：原始 ODOM 与 FLASER 分开排序，保留真实微秒时间和来源行。
激光角度与外参先沿用已归档适配器的明确约定，并校验当前数据是否满足。
这验证框架和真实观测建图，不验证定位精度、实机闭环运动或割草安全。
